# debug-trace

## 何时使用
- 用户贴了报错信息（traceback、error log、panic）
- 用户说"不工作"、"跑不起来"、"出错了"、"报错"
- 用户说"这段代码有问题"但**没说具体问题**（先按本流程排查再讨论）
- **不**用于：性能优化、重构、新功能开发

## 操作步骤（顺序严格，不跳）

### 1. 拿全错误信息
- 用户只贴了错误**最后一行** → **必须**问要完整 traceback / log
- 错误信息缺失行号或文件路径 → 让用户重跑加 `-v` / `--debug` / 设 `set -x`
- **不要凭最后一行报错猜根因**

### 2. 复现优先于猜测
```
run_command: <用户给的复现命令>      # 看自己能否复现
```
- 能复现 → 进入第 3 步
- 不能复现 → 问环境差异（OS、版本、env vars、最近改动）
- 间歇性 bug → 问"上次正常是什么时候，期间改了什么"

### 3. 定位代码现场
按 traceback **最深一帧**（最靠近错误的那个）开始：
```
read_file: <错误堆栈最深那个文件>     # 读出错的函数及上下文
```
看清楚：
- 出错那行的输入数据是什么
- 这个函数被谁调用、传了什么参数
- 最近这个文件被改过吗 → `run_command: git log -5 -- <file>`

### 4. 形成假设，再验证
**禁止跳过这步直接改代码。** 用 1-2 句话写下假设：
> 假设：参数 X 在某条路径下为 None，导致 Y 函数调用失败

然后**最小成本验证**：
- 加 `print` / `logger.debug` 看实际值（验证完删除）
- 写一个最小复现脚本，2-3 行
- 不要直接改业务代码

### 5. 修复
**只改根因**，不要顺手清理周围代码。每次改动要能回答：
- 这一行/这一段，**为什么之前坏了**？
- 这一改，**为什么这次好了**？
- 是否引入新风险（新代码路径、新依赖）？

### 6. 验证 + 写测试
```
run_command: <复现命令>               # 确认 bug 消失
```
若是逻辑 bug，**必须**加一个会捕获此 bug 的测试用例（避免回归）。

## 注意事项

### 反模式（绝对不做）
- ❌ "我加个 try/except 把它吞掉"——除非真的是预期可恢复错误
- ❌ "我加个 if 判空"——空值是症状不是原因，问"为什么这里会是空"
- ❌ "重启就好了"——能 work 不代表理解了根因
- ❌ "改一下试试"——猜测式修改污染上下文，做了 N 次后已经不知道哪条改有用
- ❌ 不重现就动手改

### 沟通规范
- 每个假设都说"我假设是 X，因为 Y"——让用户能挑战
- 不确定时直说"不确定"，不要自信硬上
- 修复前**必须**让用户看到你的假设和打算怎么改
