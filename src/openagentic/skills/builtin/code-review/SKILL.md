# code-review

## 何时使用
- 用户说"review"、"评审"、"审一下"、"看看有什么问题"
- 用户给了 PR 编号 / diff 文件 / 具体文件路径要求审阅
- **不**用于：编写新代码、解释代码（那是普通问答）

## 操作步骤

### 1. 确定审阅范围
优先级从高到低：
1. 用户给了 PR 链接 → `gh pr diff <num>` 看完整 diff
2. 用户给了文件路径 → `read_file` 全读
3. 用户没说具体范围 → `run_command: git diff` 看当前未提交改动；若空则 `git diff HEAD~1`

### 2. 按"问题等级"分类检查

#### 🔴 阻塞级（必须修）
- **安全**：SQL 注入、命令注入、路径穿越、敏感信息硬编码（API key、密码）
- **正确性**：空指针、未关闭的资源（file/conn/lock）、并发竞态、错误的边界条件
- **数据丢失**：删除/覆盖文件无确认、数据库迁移无 downgrade
- **破坏 API 兼容**：公开接口签名改了但没标 deprecated

#### 🟡 改进级（建议修）
- 异常吞掉（`except: pass`）、日志缺上下文、重复代码（DRY 违反）
- 函数 >100 行、嵌套 >4 层、神奇数字
- 命名不达意（`tmp` `data` `result` 满天飞）
- 缺测试（关键逻辑无 unit test 覆盖）

#### 🟢 风格级（可选）
- 注释、命名风格、import 顺序、空行 —— 这类**只在仓库有明确规范时才提**

### 3. 输出格式

```markdown
## Review: <文件名 / PR 标题>

### 🔴 阻塞 (N)
1. **<文件:行号>** <问题描述>
   ```<lang>
   <有问题的代码片段>
   ```
   建议：<具体怎么改>

### 🟡 改进 (N)
（同上格式）

### 🟢 风格 (N)
（同上格式，简短即可）

### 总结
- 整体评价：<2-3 句>
- 是否建议合并：合并 / 修改后再合 / 拒绝
```

## 注意事项

### 不做的事
- ❌ 不写"这段代码看起来挺好的"——没价值。要么找出问题，要么明说"未发现明显问题"
- ❌ 不堆砌纯风格意见（缩进、命名）作为主要内容——那是 linter 的活
- ❌ 不要求重写整个文件——给定点修改建议
- ❌ 不揣测意图：看不懂的地方直接问"这里 X 的目的是？"，不要瞎评

### 强约束
- 每条问题**必须**给出**文件路径 + 行号**（除非真的是全文范围问题）
- 每条问题**必须**给出**具体修改建议**（不是"考虑优化")
- 大于 3 条阻塞级问题就**不要继续看后续**——先让用户修了再来
