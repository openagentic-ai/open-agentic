# simplify

## 何时使用
- 用户说"简化"、"simplify"、"精简"、"重构一下"、"代码太长了"
- 用户刚完成一轮改动，想检查有没有写重复或多余的代码
- 用户说"看看有没有可以优化的地方"（特指简化/去重，非性能优化）
- **不**用于：性能优化（profile-driven）、架构重构（那是设计决策）

## 操作步骤

### 1. 确定审查范围
1. 用户给了文件路径 → `read_file` 全读
2. 用户没说范围 → `run_command: git diff` 看最近改动；若空则 `git diff HEAD~1`
3. 若改动涉及多个文件 → 逐个 read，关注跨文件重复

### 2. 按"简化机会"分类检查

#### 🔴 必须简化（有实质危害）
- **三份以上重复代码**：同样的逻辑出现在 ≥3 个地方
- **死代码**：永不执行的分支、定义但未调用的函数、`if False:` 这类
- **无用抽象**：只有一个调用者的 3 行函数、"Future-proof" 的扩展点
- **过度配置**：可配置的参数实际只有一个值、YAGNI

#### 🟡 建议简化（降低维护成本）
- **两处重复**：同样的逻辑出现 2 次（提取函数/变量）
- **函数过长**：>80 行且内部有明显的阶段分段
- **参数过多**：函数参数 >5 个（考虑用 dataclass / TypedDict 聚合）
- **嵌套过深**：if/for/try 嵌套 >4 层（early return / guard clause 展开）
- **复杂表达式**：单行条件/推导式超过 120 字
- **重复 import 模式**：多个文件 import 同一组东西（缺 `__init__.py` re-export）

#### 🟢 可选简化（锦上添花）
- **变量内联**：只用一次的变量且表达式不复杂
- **冗余 else**：if 块有 return 时后面的 else 可以去掉
- **`.copy()` 不必要**：dict/list 构建时就已经是新对象
- **f-string 替代 `.format()` / `%`**
- **合并相邻同类操作**：两个 `if x` 可以合并

### 3. 简化原则

```
改前 3 问：
1. 简化后行为完全一致吗？（是 / 否 → 不能改）
2. 简化后更容易读吗？（是 / 否 → 不值得改）
3. 改动的范围可控吗？（是 / 否 → 拆分小 PR）
```

### 4. 输出格式

```markdown
## Simplify: <范围>

### 🔴 必须简化 (N)
1. **<文件:行号>** — <问题描述>
   ```<lang>
   // BEFORE: <原代码>
   ```
   ```<lang>
   // AFTER:  <简化后>
   ```
   **理由**：<为什么简化后更好，1 句话>

### 🟡 建议简化 (N)
（同上格式，可选是否写 AFTER）

### 🟢 可选 (N)
（简短列出即可，每条 1 行，不一定要写 AFTER）

### 统计
- 减少行数：~N 行
- 减少重复块：N 处
```

## 注意事项

### 不做的事
- ❌ 不改命名（那是独立的 rename 任务，不混在 simplify 里）
- ❌ 不改算法（O(n²)→O(n log n) 是性能优化，不是 simplify）
- ❌ 不提取 1 行函数（3 行以下的"抽象"往往是过度工程）
- ❌ 不引入新依赖（如用 `toolz` 替代手写 for 循环）
- ❌ 不跨层简化（如把 service 层逻辑合到 route 层）

### 强约束
- 每个简化建议**必须保证行为不变**
- 同一个文件的多个简化建议 → 合并到一个 diff 块
- 简化后**必须建议跑测试**验证行为不变
- 不可逆的简化（如删除"看起来没用"的字段）→ **必须警告**

## 参考
- Kent Beck: "Make it work, make it right, make it fast" — simplify 对应 make it right
- YAGNI: You Aren't Gonna Need It
- DRY 的边界：3 次重复再抽象，2 次重复容忍（The Rule of Three）
