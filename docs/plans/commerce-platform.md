# AI 商业平台实施计划

更新日期：2026-10-03。产品定位与地推启动方式见 [产品策略](../product-strategy.md)。本地工程交付与真实商业验收分别记录，未完成项不得标记上线。三个版本的功能见 [交付说明](../merchant-workspace.md)，底座与应用边界见 [架构约束](../commerce-architecture.md)。

## 路线与现有底座

完整商业平台改造量大；第一阶段按单行业的服务发布与预约闭环交付，每批改动可独立运行、验证。复用 Agent 引擎、模型网关、数据库、工作流、任务和已有消息入口。

商业主线优先于通用个人助手扩张。个人任务记录 Agent 办事进度，订单独立承载买卖双方、服务、价格、履约与取消状态。

领域目录与实施状态：

| 目录 | 职责 |
| --- | --- |
| `src/openagentic/merchants/` | 已实现商家组织、店主成员关系、店铺与访问隔离；成员管理待做 |
| `src/openagentic/catalog/` | 已实现服务草稿、发布、下架与公开查询；商品与实时可预约时段待做 |
| `src/openagentic/commerce/` | 已实现用户确认的预约申请、订单快照、接单、履约状态与取消；已实现固定服务的限时报价与用户确认；独立需求单与协商报价待做 |
| `src/openagentic/integrations/` | 已实现通用目录契约、导入更新、示例与 HTTP 适配器、订单投递记录/重试；真实厂商联调待做 |

当前身份与工具注册主要按用户和聊天渠道组织；文件、邮件、日历连接器不能直接视为商业连接器。现有 ToolGateway 的危险操作检测主要记录日志，不能据此认定交易授权已完整实现。

## P0：地推试点与真实预约闭环

- [ ] 确定试点区域、行业、商家与客户来源。
- [ ] 明确该行业的服务字段、报价方式、预约规则、取消规则和支付边界。
- [ ] 建立商家组织、成员权限、最小商家资料和数据隔离。
  - [x] 店铺创建与编辑、创建者店主关系、服务端归属校验。
  - [ ] 团队成员邀请与角色管理。
- [ ] 建立服务发布、价格与可用性维护能力。
  - [x] 服务草稿、价格、时长、服务安排说明、发布与下架。
  - [ ] 可预约时段与实际可用性确认。
- [ ] 提供手机浏览器可用的商家工作台及客户扫码/链接入口。
  - [x] 响应式工作台、公开店铺与分享链接，前端构建通过。
  - [x] 离线二维码生成与独立解码验证。
  - [ ] 实机扫码与地推体验验收。
- [x] 接入 Agent 工具：发现已发布服务、读取服务说明、准备报价、查询自己的订单状态；用户在页面确认后创建预约。
  - [ ] 实时时段可用性与自动锁定。
- [x] 建立最小预约订单状态机、用户确认、商家接单和履约状态反馈。
  - 期望时间由商家人工确认，不自动锁定时段；本地支付为模拟，标准 API 默认关闭。
- [x] 实现预约请求幂等、订单查询和持久化重试，数据库唯一键防重复提交。
  - 后台自动执行恢复与 PostgreSQL 并发运行验证待补。
- [x] 提供运营视图、客户来源与人工投入记录，按店主/运营身份限定访问范围。
- [ ] 地推协助商家上线，陪同完成真实订单并记录反馈。
- [ ] 统计持续使用、完成订单、复用、跨商家成交和人工投入。
- [ ] 验证能否找到一批愿意让团队接触实际经营流程的商家，并记录其当前接单与服务流程。
- [ ] 对比使用前后，验证产品能否带来订单，或明显减少接单和服务成本；分别记录新增订单与效率改善。
- [ ] 按行业实际需求周期，观察用户办成一次事以后是否再次使用。
- [ ] 逐步减少创始人亲自介入，观察商家与用户是否仍能完成业务，并记录团队承接的人工投入。

验收：商家能发布真实服务；用户 Agent 能找到并在用户确认后创建预约；商家能接单履约；用户能查询结果；重复请求不会重复下单；商家不能访问其他商家的私有客户与订单。公开服务目录与私有经营数据应分别授权。

交易数据可由商家工作台维护或从通用契约导入；具体外部 SaaS 仍需真实联调。试点规模建议为 5—10 家同类商家，最终按实际资源确定，不承诺固定工期。

技术闭环验收与商业验证分别记录。扩大试点前，复核上述四项商业验证结果；证据不足时，先查明商家接入、产品价值、用户再次使用或人工依赖中的具体问题，再调整产品和启动方式。

## P1：开放接入与可靠运营

- [x] 定义稳定的商业 API：查询、报价、下单、取消、履约查询。
- [x] 定义商家能力描述、版本、输入输出以及鉴权方式。
- [x] 在服务端执行用户授权、商家权限和调用审计。
- [x] 实现一个真实或示例外部商家系统适配器，明确区分模拟与生产接入。
- [ ] 接入首个真实 SaaS，明确商品、价格、订单同步及数据来源。
- [x] 用一个独立 Agent 客户端验证第三方接入。
- [ ] 增加必要的协议适配；所有协议共用业务授权与订单规则。
- [x] 验证订单投递幂等、持久化记录与人工重试失败恢复。
- [ ] 真实 SaaS 回调去重、状态同步与生产恢复验证。
- [x] 实现取消规则、模拟退款和售后工单处理。
- [ ] 根据真实试点反馈修订规则。

外部商家系统必须在调用时确认实际报价与可用性，避免把模型生成内容当作交易承诺。需要增加的支付能力及服务商，在场景明确后单独设计。

## P2：复制与规模化

- [ ] 在验证过的行业扩大商家密度，再复制到其他区域。
- [ ] 验证持续的跨商家用户需求与公共入口留存。
- [ ] 扩大 SaaS 合作和商家自助接入。
- [ ] 按真实需求扩展支付结算、纠纷处理、服务质量与平台运营。
- [ ] 根据商家价值与交易经济性确定收费模式。
- [ ] 有证据后扩展其他行业及其专属业务规则。

## 当前不优先

跨行业通用交易模型、大量 SaaS 同时接入、复杂支付结算、完整 Agent 市场、更多独立客户端和多 Agent 自主协作，均不作为 P0 前置条件。底座工作只有在支撑试点闭环时进入商业 P0；不要求先完成所有端、所有个人连接器和完整本地运行时。

## 交付检查

新增订单和授权能力需要有意义的回归验证：租户越权、无用户确认下单、重复请求、调用超时后的状态查询、非法状态迁移与实际履约反馈。完成项必须有可运行代码和验收证据；商业假设必须通过真实使用验证。
